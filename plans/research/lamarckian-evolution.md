# Research: Lamarckian Evolution for EvoConnect4

*Status: research only — no code changes. Written to inform a possible future OpenSpec change proposal, not to specify one.*

This document investigates a possible extension to EvoConnect4 (see `plans/evoconnect4_project_plan.md`): letting each agent run a handful of PyTorch gradient-descent steps on its own network during its lifetime, and having those *fine-tuned* weights — not the untouched genome — be what its offspring inherit. It compares that idea against the project's current pure/Darwinian neuroevolution, grounds the PyTorch mechanics in the official docs, and lays out honest tradeoffs and the structural changes it would require.

---

## 1. Overview

### 1.1 Two words that need defining first

**Darwinian evolution** (biology, and the project's current design): an individual's *genotype* (its genome — here, the flat NN weight vector plus the lifespan/mutation-rate/crossover-rate genes, plan §3.2) is fixed at birth and never changes based on what the individual experiences. What the individual does in its lifetime — the games it wins or loses — only matters indirectly, through *selection*: it affects whether and how often that individual reproduces (plan §4.3) and whether it gets culled (plan §4.5). The genome that gets copied to a child is always a mutated/recombined copy of the *original, birth-time* genome. This is exactly EvoConnect4 today: "The network is a pure phenotype: it's built fresh from a genome's weight vector, used to play games, and then discarded (or reproduced from) — nothing about its weights is ever adjusted by a gradient" (plan §3.1).

**Lamarckian evolution**: named for Jean-Baptiste Lamarck's pre-Darwinian (and biologically discredited — organisms don't actually work this way) hypothesis that traits an individual *acquires* during its life — e.g., a blacksmith's muscled arms — get passed to its offspring. As a *biological* theory this is false; genomes in real organisms don't get rewritten by lived experience. But as a *computational metaphor* borrowed by the evolutionary-computation field, it's simply an algorithm design choice: let an individual modify its own encoded parameters during its "life" (via local search — some non-evolutionary optimization method applied to one individual), and write those modified parameters back into what gets inherited. Whitley, Gordon, and Mathias's 1994 paper is the canonical reference point for this terminology in evolutionary computation and directly contrasts it with the Baldwin effect (below): ["Lamarckian Evolution, The Baldwin Effect and Function Optimization"](https://www.researchgate.net/publication/2521727_Lamarckian_Evolution_The_Baldwin_Effect_and_Function_Optimization), Whitley, Gordon & Mathias, PPSN III, 1994 — it compares hybrid GA search where local-search improvements *do* overwrite the genetic encoding (Lamarckian) against search where local-search only affects the *fitness score* used for selection but the genome copied forward is the original, pre-search genotype (Baldwinian, next paragraph).

**The Baldwin effect** is the crucial third option worth knowing, because it's a middle ground between the two, and the concrete proposal in the "Context" of this document is *not* it. Introduced computationally by Geoffrey Hinton and Steven Nowlan: ["How Learning Can Guide Evolution"](https://www.cs.toronto.edu/~hinton/absps/evolution.htm), Hinton & Nowlan, *Complex Systems* 1, 1987. Their point: "The assumption that acquired characteristics are not inherited is often taken to imply that the adaptations that an organism learns during its lifetime cannot guide the course of evolution. This inference is incorrect." An individual can *learn* (locally search) during its life, and that learning can improve its *measured fitness* (so it reproduces more, same as Darwinian selection already does here) — but the offspring still inherit the *original, un-adjusted* genome, and have to re-learn from scratch. Learning never directly writes into the genome; it only reshapes the fitness landscape the genome is being selected against, by carving out a "zone of increased fitness" around good-but-imperfect genotypes, which ordinary selection then find its way toward faster. This is strictly weaker/safer than Lamarckism (no acquired-trait inheritance at all) but still faster than pure random search.

The concrete idea under investigation — fine-tune an agent's weights during its games, and have the *fine-tuned* weights themselves get copied into children's starting genome — is unambiguously **Lamarckian**, not Baldwinian: the modified weights are inherited directly, not merely used to compute a fitness score.

### 1.2 How this differs from EvoConnect4 today

| | Current (Darwinian) | Proposed (Lamarckian hybrid) |
|---|---|---|
| What plays a tick's games | The NN built from the genome's stored `nn_weights` (plan §3.1, §6) | Same — but weights may drift within the tick via gradient steps |
| What determines `fitness` | Win/draw/loss record only (plan §5) | Unchanged |
| What gets copied into a child's starting genome | The *parent's original* `nn_weights`, then crossover + mutation (plan §3.3) | The parent's *fine-tuned, post-gradient-step* `nn_weights`, then crossover + mutation |
| Source of all long-run improvement | Selection + mutation + crossover, across the *population*, over many ticks | Same population-level mechanisms, *plus* each individual's own local optimization compounding into the gene pool every time it reproduces |
| Anything trained by gradient descent | Never — the plan is explicit that "there is no backpropagation and no reinforcement-learning gradient anywhere in the loop" (plan §1) | This is the one place it would be introduced, and only as an optional mode |

### 1.3 Why it's a plausible speedup

Pure mutation-and-selection is a *blind* search: a mutated weight vector is evaluated only by playing it out and seeing whether it wins more games than its rivals; there's no gradient telling any individual weight which direction would help. A gradient step, by contrast, uses local, per-weight error signal computed directly from that agent's own games. In principle this lets one agent's single lifetime do a small amount of directed local optimization that would otherwise require many generations of lucky mutations landing in the right direction to discover blindly. Combined with inheritance, that local improvement compounds across the population as fine-tuned lineages out-reproduce non-fine-tuned ones (via the existing fitness-driven reproduction-interval mechanism, plan §4.3) — this is the mechanism the neuroevolution literature reports measurable gains from; see §1.4 below for concrete prior results.

### 1.4 Prior art establishing this is a known, studied technique

This is not a novel idea specific to this project — it's a recognized sub-area of neuroevolution:

- **Direct precedent — Lamarckian evolution of neural network *weights* specifically**: Ku, Mak & Siu, ["A study of the Lamarckian evolution of recurrent neural networks"](https://www.researchgate.net/publication/220489390_Lamarckian_Evolution_and_the_Baldwin_Effect_in_Evolutionary_Neural_Networks), *IEEE Transactions on Evolutionary Computation* 4(1), 2000, pp. 31–42 (an earlier related paper, same authors: ["Adding learning to cellular genetic algorithms for training recurrent neural networks"](https://www.researchgate.net/publication/220578070_A_Lamarckian_Approach_for_Neural_Network_Training), *IEEE Trans. Neural Networks* 10, 1999, pp. 239–252). Their finding, as reported: local search and evolutionary search "complement each other to yield a better training algorithm," and the combination is "particularly efficient when the local search is simple" — directly relevant, since this project's local search (a handful of TD steps, §2.3) would be about as simple as local search gets.
- **Direct precedent — Lamarckian weight inheritance for CNNs, with measured cost/benefit**: ["Lamarckian Evolution of Convolutional Neural Networks"](https://arxiv.org/abs/1806.08099), 2018 (PPSN/arXiv 1806.08099). Reports that inheriting gradient-trained weights across generations, versus not inheriting them, achieved "similar or significantly better test accuracies," faster convergence, and roughly 75% better data efficiency on CIFAR-10/100 — i.e., a real, measured win for the same core mechanism proposed here (inherit locally-trained weights, don't restart from the raw genome each generation).
- **The classical caution — Lamarckian is not always better than Baldwinian**: the Whitley, Gordon & Mathias 1994 paper cited in §1.1 found that on some functions, *pure Lamarckian* evolution converges to local optima that Baldwinian (learn-but-don't-inherit) search escapes, because forcing every genotype to match its locally-optimized phenotype can destroy the population diversity needed to keep exploring. This is the direct literature basis for the diversity-collapse risk flagged in §3 below — it is a documented failure mode, not a hypothetical one.
- **Hybrid evolution + gradient learning in RL-flavored settings** (a different but related mechanism — periodic *injection* of a gradient-trained network into an evolving population, rather than continuous per-individual fine-tuning): Khadka & Tumer, ["Evolution-Guided Policy Gradient in Reinforcement Learning"](https://arxiv.org/abs/1805.07917) ("ERL"), NeurIPS 2018. Their algorithm "leverages the population of an EA to provide diversified data to train an RL agent, and reinserts the RL agent into the EA population periodically to inject gradient information into the EA" — evidence from the field that mixing gradient-based learning into a neuroevolution loop, even loosely, measurably improves on both pure-EA and pure-RL baselines on their continuous-control benchmarks.
- **Self-adaptive parameters, the mechanism this project already uses for `mutation_rate`**: Schwefel's self-adaptive evolution-strategies technique (surveyed in Beyer & Schwefel, ["Evolution Strategies – A Comprehensive Introduction"](https://www.semanticscholar.org/paper/Evolution-strategies-%E2%80%93-A-comprehensive-introduction-Beyer-Schwefel/8a7a9672b4981e72d6e9206024c758cc047db8cd), *Natural Computing* 1, 2002) is the well-known ancestor of this project's self-adaptive σ gene (plan §3.2, "a small, well-known trick from evolution-strategies research"). It's relevant here because it establishes that this project's evolutionary mechanics are already, deliberately, drawn from the evolution-strategies tradition — and that tradition is exactly where the Lamarckian/Baldwinian distinction was worked out most rigorously (§3.3 discusses the specific interaction risk between self-adaptive σ and Lamarckian fine-tuning).

## 2. PyTorch specifics

### 2.1 The network module: current numpy vs. a `torch.nn.Module`

**Current design (plan §7, `src/evoconnect4/agent/network.py`, not yet built):** "feedforward NN: build from a flat weight vector, forward pass." Per plan §3.1, that's 42 inputs → 24-neuron tanh hidden layer → 7 linear outputs, ~1,200 weights+biases total, and per plan §7's rationale table: "nothing here needs autograd since nothing is trained by gradient." In numpy this is two small matrix multiplies plus a `tanh`, reshaped out of one flat `np.ndarray` — genuinely just arithmetic, no framework needed.

**What a `torch.nn.Module` version looks like.** Per the official docs (["Module — PyTorch documentation"](https://docs.pytorch.org/docs/stable/generated/torch.nn.Module.html)): "Your models should subclass this class... an `__init__()` call to the parent class must be made before assignment on the child," and layers assigned as attributes in `__init__` (e.g. `nn.Linear`) "will be registered, and will also have their parameters converted when you call `to()`, etc." — i.e., PyTorch auto-discovers every weight/bias tensor that needs a gradient just by how you assign it in `__init__`, and `forward()` (per the same docs: "Define the computation performed at every call. Should be overridden by all subclasses") is where the actual math goes:

```python
import torch
import torch.nn as nn

class Connect4Net(nn.Module):
    def __init__(self, hidden_size: int = 24):
        super().__init__()
        self.hidden = nn.Linear(42, hidden_size)
        self.output = nn.Linear(hidden_size, 7)

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        x = torch.tanh(self.hidden(x))
        return self.output(x)   # raw per-column scores, same as today
```

This is structurally identical to the planned numpy version (same shapes, same `tanh`, same "one raw score per column" output) — the only difference is that PyTorch tracks the computation graph so gradients *can* be computed, which the numpy version deliberately can't do.

### 2.2 What autograd actually does, concretely

Per the official autograd tutorial (["A Gentle Introduction to torch.autograd"](https://docs.pytorch.org/tutorials/beginner/blitz/autograd_tutorial.html)): every `nn.Parameter` (which is what `nn.Linear` registers for you) has `requires_grad=True` by default, and PyTorch "calculates and stores the gradients for each model parameter in the parameter's `.grad` attribute" once you call `.backward()` on a scalar loss. The trigger for computing/applying a gradient step is the standard three-call pattern documented at [`torch.optim`](https://docs.pytorch.org/docs/main/optim.html):

```python
optimizer.zero_grad()   # clear .grad from the previous step
loss = loss_fn(...)
loss.backward()         # populate .grad on every parameter via the chain rule
optimizer.step()        # apply the update using .grad
```

For any code path that should *not* accumulate gradient history (e.g., ordinary move-selection during normal play, which shouldn't build up a computation graph for every game), the same autograd docs describe `torch.no_grad()` as a context manager that disables gradient tracking for a block of code — this matters for keeping ordinary (non-training) forward passes cheap, since without it PyTorch would otherwise track the full graph on every move an agent makes, most of which are never going to be backpropagated through.

### 2.3 Loss function: TD-learning as the self-supervised signal

**What "TD-learning" (temporal-difference learning) means, defined on first use:** it's a way to learn to predict an eventual outcome (here: did this agent's game end in a win, draw, or loss) *without* waiting until the game ends to get every training signal. Instead of only comparing "my prediction at move `k`" to "the final result," TD-learning also compares each prediction to the *next* prediction, and nudges the earlier one toward the later one. Formally, per Sutton's foundational paper (["Learning to Predict by the Methods of Temporal Differences"](https://www.researchgate.net/publication/225264698_Learning_to_Predict_by_the_Method_of_Temporal_Differences), *Machine Learning* 3(1), 1988, pp. 9–44): TD methods use "the difference between two successive predictions" as the training error at each step, rather than waiting for the final outcome every time — "it is not necessary to wait for the outcome... at each step the difference between two successive predictions is used."

**Why this is the right fit here, and its proven track record in exactly this kind of game:** this project's networks already output "one raw score per column" (plan §3.1) rather than a position-value estimate, so the most direct adaptation is a value head: interpret the network's evaluation of a resulting board position as an estimate of that position's eventual outcome for the mover, and train it with TD(λ) — the same architecture and training rule used by Gerald Tesauro's TD-Gammon, one of the most-cited successes of self-supervised, self-play learning in a two-player game:

- ["Temporal Difference Learning and TD-Gammon"](https://www.bkgm.com/articles/tesauro/tdl.html), *Communications of the ACM* 38(3), 1995, pp. 58–68. Update rule as stated: `w[t+1] - w[t] = α(Y[t+1] - Y[t]) Σ_{k=1}^{t} λ^{t-k} ∇_w Y[k]` — i.e., adjust weights to make each position's predicted outcome `Y[t]` closer to the *next* position's predicted outcome `Y[t+1]`, with credit assigned back over the game's move history via the `λ` decay term. "During training, the neural network itself is used to select moves for both sides" — pure self-play, no external teacher or labeled dataset, which is exactly this project's situation (games are generated by agents playing each other, plan §4.2, and there is no source of "correct move" labels anywhere). Tesauro reports this reached master-level backgammon play from "zero initial knowledge" starting weights.

Concretely for this project: after an agent finishes its games in a tick, replay the sequence of board positions it saw (already recorded — `move_history` is stored per game per plan §6's `games` table), compute the network's scalar value estimate for each position (e.g., a small additional linear "value" output, or `max` over the column-score head, reinterpreted as a position value), and apply the TD(λ) update — or, as a simpler first cut given the project's small scale, plain outcome regression: treat the final game result (`+1` win / `0` draw / `-1` loss, from the mover's perspective, consistent with the existing input encoding in plan §3.1) as a one-shot regression target for every position seen in that game, and use ordinary MSE loss (`nn.MSELoss` — standard PyTorch loss module) instead of full TD(λ). This drops the `λ`-weighted credit assignment machinery but keeps the essential "self-supervised, no external labels, signal derived only from the game's own outcome" property the design asked for, and is markedly simpler to implement and debug first — TD(λ) is the natural upgrade once outcome regression is working, not necessarily the required starting point.

### 2.4 Optimizer and step count at this project's scale

Per the official `torch.optim` docs: "To construct an Optimizer you have to give it an iterable containing the parameters to optimize... then you can specify optimizer-specific options such as the learning rate." Given ~1,200 parameters (plan §3.1) and a handful of positions per game, this is a tiny-data, tiny-model regime — nowhere near the scale `Adam` or large learning-rate schedules are designed for:

- **Optimizer**: plain `torch.optim.SGD` with a small learning rate (e.g. `lr=0.01`–`0.05`) is a reasonable, simple starting point — no momentum needed at this scale, and it avoids `Adam`'s per-parameter adaptive state (`betas`, running moment estimates) needing to be reset or carried between agents, which would otherwise be one more piece of hidden per-agent state to manage correctly. `Adam`'s documented default (`torch.optim.Adam(params, lr=0.001, betas=(0.9, 0.999), eps=1e-08, ...)`, per [the Adam docs](https://docs.pytorch.org/docs/stable/generated/torch.optim.Adam.html)) is a fine fallback if plain SGD proves too finicky to tune, but adds complexity this project's scale probably doesn't need yet.
- **Steps per tick**: a handful — think single digits (e.g. 5–20 gradient steps per agent per tick, over the ~10–20 positions from that tick's 2 games, plan §4.2's `games_per_pair_per_tick: 2`). This is a toy-scale, cheap local nudge in the spirit of Ku/Mak/Siu's finding that Lamarckian gains showed up even with "simple" local search (§1.4) — not a full training run. Because the population is ~100 agents (plan §10) and a run spans "hundreds of ticks" (plan §12), even a handful of gradient steps per agent per tick multiplies out to a large total step count over a full run; see §3.1 for the compute-cost accounting.

### 2.5 Converting fine-tuned torch weights back to the genome's flat numpy vector

This is the piece that has to be airtight for the rest of the system (mutation, crossover, DB storage — plan §3.2, §3.3, §6) to keep working *unchanged*, since all of that machinery is written against "the genome's flat numpy weight vector."

- **numpy → torch, for loading a genome into a network to play/train:** `torch.from_numpy(flat_weights)` (standard bridging function, [`torch.from_numpy` docs](https://docs.pytorch.org/docs/stable/generated/torch.from_numpy.html)) creates a tensor that *shares underlying memory* with the numpy array rather than copying it — worth knowing, but for safety this project should still copy explicitly (`torch.from_numpy(flat_weights.copy())` or reshape into the module's parameter tensors via `.data.copy_(...)`) rather than relying on aliasing, so a numpy array stored elsewhere (e.g. the original genome kept for comparison) can't be silently mutated by a later in-place torch operation.
- **Reshaping the flat vector into the module's actual per-layer weight/bias tensors:** the flat vector's layout (which plan §3.2 already specifies must be defined — "NN weights: every weight & bias in the network, flattened to one vector") has to match the order `Connect4Net`'s `state_dict()` produces. The clean way to do this without hand-rolling offset arithmetic twice (once for numpy reshape, once for torch): use the module's own `state_dict()` (per [the `nn.Module` docs](https://docs.pytorch.org/docs/stable/generated/torch.nn.Module.html): "Return a dictionary containing references to the whole state of the module") to get the canonical parameter shapes and iterate them in that fixed order when flattening/unflattening, rather than hardcoding shape offsets by hand in two places. `load_state_dict(state_dict, strict=True)` ("Copy parameters and buffers from `state_dict` into this module and its descendants") is the paired call for loading a set of numpy-derived tensors back into a fresh `Connect4Net` instance.
- **torch → numpy, after fine-tuning, to write back into the genome:** for each parameter tensor, `.detach()` first (drop it from the autograd graph — required, since a tensor still attached to the graph can't be converted) then `.numpy()` (or `.cpu().numpy()` if this ever runs on GPU, unlikely to matter at this scale) — i.e. `param.detach().numpy().flatten()` per parameter, concatenated in the same fixed `state_dict()` order used above, producing a plain `np.ndarray` that goes straight back into `nn_weights` (plan §6) with zero changes to how the rest of the system reads or writes that field.
- **Net effect:** everything downstream of "the genome has a flat numpy weight vector" — mutation (Gaussian noise added elementwise, plan §3.2), crossover (uniform per-weight selection, plan §3.3), and the `agents.nn_weights` DB column (plan §6) — never needs to know PyTorch was involved. PyTorch is a purely *internal* detail of one optional step (`agent/network.py`'s torch-backed fine-tuning path, if added, §4 below); the boundary in and out of it is a flat `np.ndarray`, both directions.

## 3. Tradeoffs

### 3.1 Compute cost

The multiplication is the headline cost. Population ~100 agents (plan §10 default `population_size: 100`), runs of "several hundred ticks" (plan §12's Definition of Done), each agent playing 2 games/tick when paired (plan §10 `games_per_pair_per_tick: 2`). If every alive agent runs, say, 10 gradient steps per tick it participates in, that's on the order of `100 agents × hundreds of ticks × 10 steps` — tens to hundreds of thousands of small gradient updates over a full run, on top of the game-playing compute that's already there. Each individual step is cheap (forward + backward pass through ~1,200 parameters is trivial on a CPU), but it's a real multiplicative factor on top of a simulation whose entire current design is deliberately numpy-only and "small enough to evolve quickly" (plan §3.1). Salimans et al.'s evolution-strategies paper is a useful point of comparison for how compute-conscious this whole family of algorithms tends to be at scale — their headline contribution was specifically making a *gradient-free* population method "scale extremely well with the number of CPUs available" by communicating only scalars ([Evolution Strategies as a Scalable Alternative to Reinforcement Learning](https://arxiv.org/abs/1703.03864), Salimans, Ho, Chen, Sidor & Sutskever, 2017) — a reminder that this project's existing pure-evolution design already sits in a lineage that prizes cheap-per-individual, embarrassingly-parallel evaluation, and adding a per-individual gradient loop cuts somewhat against that grain.

### 3.2 New dependency cost

`pyproject.toml` currently declares exactly two runtime dependencies: `numpy>=2.5.2` and `pyyaml>=6.0.3` (confirmed by reading the file directly). Adding `torch` is a materially heavier dependency than either — PyTorch's installed wheel size is commonly hundreds of MB (versus numpy's tens of MB), pulls in its own native binary/BLAS stack, and (depending on platform) may pull CUDA-related packages even for a CPU-only, ~1,200-parameter toy model that will never benefit from a GPU. For a project explicitly framed as "a toy project" whose stated selling point is "no external dependencies" for the game engine (plan §2, "Quick to implement... with no external dependencies") and "nothing here needs autograd since nothing is trained by gradient" as the *reason* numpy was chosen (plan §7's architecture table), pulling in a full deep-learning framework for a handful of tiny gradient steps is a heavy tool for a light job — worth naming plainly rather than glossing over.

### 3.3 Evolutionary/algorithmic risks

- **Diversity collapse.** This is the sharpest risk, and it's not speculative — it's the literature's central finding about Lamarckian evolution specifically. Whitley, Gordon & Mathias (1994, §1.1/§1.4 above) found cases where Lamarckian inheritance converges the population to a local optimum that a Baldwinian (learn-but-don't-inherit) or purely Darwinian process would have escaped, precisely because forcing every genotype to match its own locally-optimized phenotype removes genetic variation faster than mutation can replace it. In this project's terms: if every agent's TD fine-tuning nudges its weights toward "whatever locally reduces prediction error given its own recent opponents," and *that* is what gets inherited every reproduction cycle, the population can homogenize around one local strategy much faster than the existing mutation/crossover/culling machinery (plan §4) is tuned to counteract — undermining exactly the "co-evolutionary blind spot" concern the plan already flags in §14 ("a population can plateau or even quietly cycle... while internal fitness numbers look fine").
- **Interaction with the self-adaptive mutation-rate gene (σ, plan §3.2).** σ is designed to self-tune based on which mutation strengths *actually produce fitter descendants* over evolutionary time. If a large share of an agent's fitness gain now comes from within-lifetime gradient fine-tuning rather than from the inherited genome's raw quality, σ's feedback signal gets muddied — a lineage might drift toward smaller σ (less mutation) not because small mutations are genuinely better, but because gradient fine-tuning is quietly doing the exploration/correction work that mutation used to be credited for, which could mask or distort the "does mutation strength settle somewhere sensible, or drift to an extreme" question the plan already asks in §9/§14.
- **Local fine-tuning drowning out the evolutionary signal.** If the gradient step size or step count is too large relative to the mutation step, an agent's post-fine-tuning weights could end up dominated by "what TD-learning on ~10-20 recent positions happened to nudge toward" rather than by "what the genome's crossover/mutation history actually encodes" — at that point the system stops being meaningfully evolutionary at all and becomes closer to "population-based hyperparameter search around a bunch of independently-gradient-trained networks," which is a different (and reasonable!) algorithm, but not the one described in plan §1 ("no backpropagation and no reinforcement-learning gradient anywhere in the loop... The only source of improvement... is selection, mutation, and (optionally) crossover"). Keeping the fine-tuning step small/cheap relative to the mutation step (§2.4) is the main lever to keep this from happening, but it's a balance that would need tuning and watching, not a one-time setting.
- **A real, literature-backed *upside* worth weighing against the above**: this isn't purely a cautionary story — Ku/Mak/Siu and the CNN Lamarckian-evolution paper (§1.4) both report genuine wins from this exact mechanism (better sample efficiency, faster convergence) when the local search is kept simple and cheap relative to the evolutionary process around it. The risk above is real but conditional on getting the balance wrong, not inherent to the idea.

### 3.4 Honest read: is it worth it for this project?

For a **toy/learning project** whose explicit point (per the plan's own framing throughout — "no backpropagation and no reinforcement-learning gradient anywhere in the loop," "closed ecosystem," "purely through evolution") is to explore and understand *pure* neuroevolution mechanics end-to-end — steady-state population dynamics, self-adaptive mutation, fitness-driven reproduction timing — adding Lamarckian fine-tuning is a genuinely separate research question, not a natural next increment. It would:
1. Introduce a heavyweight new dependency (§3.2) for a feature orthogonal to the project's stated learning goal.
2. Blur the clean, current story of "everything the population learns, it learns through selection alone" — which is arguably the most pedagogically valuable and legible property of the MVP as planned, especially for someone new to both neural networks and evolutionary algorithms trying to build intuition for what pure selection *can* and *can't* do unaided.
3. Add a second axis of tuning (fine-tuning learning rate, step count, loss function, how it interacts with σ) on top of an already nontrivial set of evolutionary hyperparameters (plan §10), which raises the chance that a run behaving oddly is now ambiguous between "an evolution bug" and "a gradient-descent bug."
4. Only pay off *if* the population-level speedup is large enough to justify all of the above — and per §1.4, the literature says this is real but context-dependent (Ku/Mak/Siu explicitly caveat it works "particularly" well when local search is *simple*; Whitley et al. show it can also actively hurt).

The more honest framing: build and finish the pure-evolution MVP first (Phases 2–8, plan §11) and *observe* whether it plateaus or struggles to find good play within a reasonable tick budget. If it does, Lamarckian fine-tuning is one of several credible fixes worth prototyping alongside the other extensions already listed in plan §13 (hall-of-fame opponents, fresh-blood injection, speciation) — but it's the most structurally invasive of that list (new dependency, new per-agent computation, a second learning mechanism entirely), so it's worth treating as its own scoped experiment/OpenSpec change with its own success criteria (e.g., "does baseline-benchmark win-rate, plan §5, improve faster per-tick than the pure-evolution baseline, at what compute cost, and does population gene diversity, plan §9, hold up") rather than folding it into the core plan by default. Building it *toggleable* (§4 below) is what makes that honest A/B comparison possible later without committing to it now.

## 4. Structural changes needed

All changes below are additive and gated behind a config flag, so the existing pure-evolution path is unaffected when the flag is off. Nothing here should be built now — this section exists to make a future OpenSpec change proposal concrete, per the brief.

- **`pyproject.toml`** — add `torch` as a dependency, but only if this mode is pursued; ideally as an optional extra (e.g. `[project.optional-dependencies] lamarckian = ["torch>=..."]`) rather than a hard runtime dependency, so the default install stays numpy-only and lightweight, matching the project's stated minimal-dependency ethos (§3.2 above).

- **`config.yaml`** — a new, clearly-delineated section, off by default, e.g.:
  ```yaml
  lamarckian_learning:
    enabled: false
    optimizer: sgd
    learning_rate: 0.02
    steps_per_tick: 10
    loss: outcome_regression   # or td_lambda
    td_lambda: 0.7             # only used if loss: td_lambda
  ```
  This keeps every new tunable in the same single human-editable place the plan already establishes for everything else (plan §10), and `enabled: false` as the default is what makes the feature strictly optional rather than a redesign of the existing pipeline.

- **`src/evoconnect4/agent/network.py`** — currently planned to be a pure-numpy "build from a flat weight vector, forward pass" module (plan §7). Two reasonable approaches:
  1. Keep the numpy implementation as the default/always-used inference path (fast, dependency-light, used for every ordinary game), and add a separate, optional torch-backed module (e.g. `network_torch.py`, imported only when `lamarckian_learning.enabled: true`) used *only* during the fine-tuning step, converting to/from the flat numpy vector at the boundary as described in §2.5. This isolates the new dependency to one file that most of the codebase, and most contributors, never need to touch.
  2. Alternatively, make `network.py` itself torch-backed always, and drop numpy for network math entirely — simpler long-term (one implementation, not two to keep in sync) but forces the `torch` dependency onto every user of the project, even ones who never want Lamarckian mode. Given §3.2's dependency-weight concern, option 1 (numpy stays the default, torch is opt-in and isolated) is the more defensible choice for keeping the pure-evolution path exactly as lightweight as it is today.

- **`src/evoconnect4/agent/genome.py`** — no change to the genome's *shape* (still a flat numpy `nn_weights` vector plus the existing trait genes, plan §3.2); the only change is *when* `nn_weights` gets overwritten — currently only by `mutate`/`crossover` at reproduction time, and under this extension, also by the fine-tuning step during an agent's lifetime, before it next reproduces. Worth deciding explicitly (and documenting) whether fine-tuning happens *every* tick the agent plays, or only occasionally — the config's `steps_per_tick` above assumes every tick, which is the simplest semantics to reason about and test.

- **`src/evoconnect4/agent/agent.py`** — "wraps a genome + network + live stats" (plan §7). This is the natural home for a new method like `agent.fine_tune(games_this_tick)` — called once per tick, after that agent's games are recorded, taking that tick's `move_history` (already persisted per plan §6) and outcome, running the torch-backed local update, and writing the result back into `self.genome.nn_weights` via the numpy round-trip in §2.5. Keeping this as an isolated method (rather than threading torch calls through the existing forward-pass code path) is what lets it be skipped entirely, cheaply, when `lamarckian_learning.enabled` is false.

- **`src/evoconnect4/evolution/population.py`** (not yet built, plan §7/§11 Phase 4) — the tick loop (plan §4.2) gains one new step, guarded by the config flag: after "update A and B's games_played / wins / losses / draws" and before the reproduction check, call each participating agent's `fine_tune(...)` if enabled. Important ordering point: fine-tuning should happen *before* that tick's reproduction check, since the entire point of Lamarckian inheritance is that a child born this tick inherits the *already fine-tuned* weights, not the pre-tick ones.

- **`agents` DB table, `nn_weights` field (plan §6)** — no schema change needed; it's already "JSON/blob, flattened weight vector," and the fine-tuned weights are just a different set of numbers in the same shape written to the same column. The one worthwhile *addition*, for later analysis (not required to make the feature work): a boolean/enum column such as `weights_fine_tuned` or reusing `nn_architecture`'s JSON blob to note how many fine-tuning steps this agent underwent, so a future analytics pass (plan §9) could compare fine-tuned vs. non-fine-tuned lineages' fitness trajectories directly from the DB — directly useful for the "does the expected speedup materialize" evaluation called for in §3.4 above.

- **Tests** — a Lamarckian-mode test would want to check, at minimum: (a) the numpy round-trip in §2.5 is lossless in the *disabled* path (unchanged genomes produce byte-identical `nn_weights` before/after a no-op through the torch conversion, if the conversion code is shared) — this guards against silently breaking the existing pure-evolution path while wiring the new one in; (b) with the flag enabled, a single fine-tuning step measurably changes `nn_weights` in the expected direction on a toy example (e.g. loss decreases over the configured `steps_per_tick`); (c) the flag being `false` reproduces bit-identical simulation results to the current pure-numpy path on a fixed `random_seed` (plan §10), as a regression guard that the optional feature genuinely doesn't touch anything when off.
